# AI 能力补充实施方案

本文档补充现有 Prompt、RAG、Skill、Agent、长期记忆、执行事件和断点恢复能力，规划后续 AI 能力建设。目标是先提高企业私有知识库的回答质量，再扩展任务执行、企业系统连接、多模态和工作流能力。

## 1. 当前基线

已有能力：

- OpenAI 兼容模型、自动路由和模型重试；
- Prompt Registry、`legacy/v2/v2-shadow`、Prompt 哈希和上下文审计；
- 文档 RAG、Milvus/Redis 存储、来源引用和长期记忆；
- Supervisor、Knowledge Agent、Writer Agent、Skill 和工具中间件；
- WebSocket 执行事件、审批、Checkpoint、断点恢复和 Owner 隔离；
- 附件生命周期和 `internal/multimodal` 解析代码；
- `internal/dataquery`、意图路由和评测框架，但部分能力默认关闭。

当前主要缺口：

- RAG 仍以向量检索为主，缺少统一的混合检索和 Reranker；
- Agent 没有通用 Goal/Todo、计划、验收和自检闭环；
- 没有 MCP Client 和标准化外部能力接入层；
- 多模态 Provider、附件前端展示和真实样本验收尚未完成；
- 没有可配置 Workflow、Workspace Agent、代码沙箱和 Vibe Coding 闭环；
- 没有 Graph RAG、模型微调和在线人工反馈闭环。

## 2. 总体原则

1. **先质量，后扩展**：优先改善私有知识问答，避免先做复杂平台能力。
2. **兼容现有链路**：保留现有 Agent、工具、RAG、记忆和执行事件接口。
3. **每项能力独立开关**：默认关闭新能力，支持灰度启用和立即回滚。
4. **只读优先**：外部系统和 MCP 先开放查询，写操作必须有权限、审批和幂等键。
5. **证据优先**：所有事实回答必须能追溯到文档、长期记忆、附件或实时数据来源。
6. **不保存敏感正文**：继续使用哈希、摘要和来源元数据审计，避免把完整 Prompt、文件正文和私有上下文写入执行日志。

## 3. 实施阶段

### P0：私有知识库质量增强

**目标**：提高召回准确率、引用可信度和长期记忆可见性。

**预计工作量**：2～4 周，约 10～20 个核心文件；新增常驻内存约 100～300MB，正常运行预留 300MB～1GB。

**实施内容**：

1. 在 `internal/eino/rag` 增加关键词/字段过滤与向量检索的统一接口；
2. 增加可替换的 Reranker 接口，先支持外部服务或本地 HTTP Provider；
3. 增加查询改写、TopK 合并、去重和父文档/来源聚合；
4. 为每个检索结果保留 `source_ref`、分数、检索方式和时间；
5. 增加引用完整性检查，阻止答案引用不存在或不支持结论的来源；
6. 增加低分、冲突和无依据回答策略；
7. 在执行事件中记录 `memory_hit`、`memory_count`、`knowledge_hit` 和来源类型；
8. 扩展 `internal/evaluation`，增加召回率、引用覆盖率、拒答率和无关检索率。

**建议开关**：

```yaml
rag:
  hybrid_search: false
  reranker:
    enabled: false
    provider: ""
    top_k: 10
  citation_guard:
    enabled: true
```

**验收标准**：

- 现有向量检索结果不因新开关关闭而变化；
- 混合检索在固定评测集上提升召回率；
- 低分结果不会被写成确定项目事实；
- 引用来源真实存在且能支持答案；
- 普通问题不触发无关知识库或记忆检索；
- 长期记忆命中能在执行事件中区分于文档命中。

### P1：通用 Agent Loop

**目标**：把固定多 Agent 对话升级为可恢复、可验收的任务执行 Agent。

**预计工作量**：3～6 周，约 20～35 个核心文件；正常运行新增约 300MB～1GB，主要取决于并发任务数和上下文长度。

**实施内容**：

1. 新增 Goal、Todo、Plan、Step 状态模型；
2. 每个任务关联已有 `run_id/turn_id/step_id/attempt_id`；
3. 增加最大 Step 数、工具调用数、重试次数和上下文预算；
4. 明确 `completed`、`blocked`、`needs_approval`、`failed`、`cancelled` 等停止原因；
5. 为工具结果增加成功条件和失败分类；
6. 增加任务完成判定和结果自检；
7. 自检失败时允许有限次数重新规划；
8. 增加人工接管点，并复用现有审批和断点恢复；
9. 任务状态和计划只保存安全摘要，不保存完整私有上下文；
10. 通过旧 Agent Loop 适配器保证原有普通问答路径不变。

**建议接口**：

```go
type Goal struct {
    ID       string
    RunID    string
    Objective string
    Status   string
}

type TodoItem struct {
    ID, GoalID, Title, Status string
    DependsOn []string
    Attempts  int
}
```

**验收标准**：

- 简单问答仍只执行一个必要步骤；
- 复杂任务能产生有限、可追踪的步骤；
- 达到上限后明确停止，不无限循环；
- 工具失败后不会重复执行不可重试操作；
- 重启后可以从最近可靠状态继续；
- 自检失败、审批等待和人工接管均能在前端执行事件中区分。

### P2：MCP 和企业外部能力

**目标**：以标准协议接入企业内部只读系统，同时复用现有权限、审批、超时、重试和审计管线。

**预计工作量**：3～5 周，约 15～30 个核心文件；每个 MCP 连接常驻约 5～30MB，连接池和缓存另计。

**实施内容**：

1. 新增 MCP Client 生命周期管理；
2. 支持工具发现、资源读取和能力版本记录；
3. 将 MCP 工具转换为现有统一 Tool 接口；
4. 为每个工具绑定 Owner、权限、超时、重试和审批策略；
5. 事件中记录服务来源、工具版本、调用摘要和结果状态；
6. 先接入一个只读系统，禁止模型直接生成任意 URL、SQL 或命令；
7. 将 `internal/dataquery` 与 MCP 适配器统一到外部能力层；
8. 失败时返回“数据不可用/权限不足”，不能退回长期记忆猜测实时状态。

**建议开关**：

```yaml
mcp:
  enabled: false
  servers: []
  allow_write: false
```

**验收标准**：

- 未登记的 MCP 服务不能被调用；
- 跨 Owner 查询返回拒绝或空结果；
- 超时、断连、401/403、空结果和上游 5xx 可区分；
- MCP 只读工具不触发写操作审批；
- 服务重启后不会遗留不可恢复的连接状态。

### P3：多模态和结构化业务能力

**目标**：完成已有附件/多模态代码的真实 Provider 验证和产品化启用。

**预计工作量**：2～5 周，约 10～25 个核心文件；单文件处理约 100MB～1GB，必须限制并发和处理时长。

**实施内容**：

1. 先启用图片和扫描 PDF 的视觉/OCR Provider；
2. 验证页码、区域、OCR 置信度和解析器版本；
3. 完成表格工作表、单元格和公式引用；
4. 完成音频时间戳、说话人和转写置信度；
5. 完成视频字幕、转写和关键帧引用；
6. 在 Web UI 显示附件状态、解析失败和来源位置；
7. 完成病毒扫描、失败重试、过期清理和删除；
8. 扩展真实样本评测，解析失败时禁止模型编造内容。

**启用顺序**：图片/扫描 PDF → 表格 → 音频 → 视频。每种模态独立开关，不打包成一次不可回滚发布。

**验收标准**：

- 文本 PDF 不重复调用 OCR；
- 图片和扫描 PDF 回答包含文件/页码/区域来源；
- 表格回答包含工作表和单元格范围；
- 音频和视频回答包含时间戳；
- Provider 不可用、置信度过低或文件越权时明确失败；
- 原文件和解析产物按 Owner 隔离。

### P4：Workflow 和 Workspace Agent

**目标**：将 Agent 能力扩展为可配置的企业任务和团队工作空间。

**预计工作量**：6～12 周，约 30～60 个核心文件；常驻内存约 200MB～1GB，运行中取决于并发流程数。

**实施内容**：

1. 定义流程节点、条件分支、循环、审批和结束状态；
2. 支持手动触发、Webhook 和定时触发；
3. 为每个节点设置超时、重试、补偿和幂等键；
4. 复用 MCP 和结构化查询作为外部节点；
5. 接入团队文档、任务系统、会议记录等经授权的 Workspace 数据；
6. 建立 Workspace、项目、Owner 和成员权限边界；
7. 增加流程执行历史、失败重试和人工接管；
8. 暂不把所有 Workspace 数据自动写入长期记忆，必须经过筛选和来源标记。

**验收标准**：

- 流程可暂停、恢复、取消和重试；
- 条件分支不能被模型任意改写；
- 节点失败不会造成重复写入；
- 不同 Workspace 之间不存在数据泄露；
- 流程执行结果可通过现有执行事件和 API 查询。

### P5：Vibe Coding Agent 和代码沙箱

**目标**：在独立仓库和隔离环境中完成代码分析、修改、测试和修复。

**预计工作量**：8～16 周，约 40～80 个核心文件；每个沙箱约 500MB～2GB，必须设置并发上限。

**实施内容**：

1. 仓库注册、分支和 Owner 隔离；
2. 只读浏览、受限文件修改和 Patch 生成；
3. 命令白名单、工作目录限制和网络隔离；
4. 测试、编译和静态检查执行；
5. 错误摘要回传给 Agent，允许有限修复循环；
6. Git diff、提交前审批和自动回滚；
7. Docker/进程沙箱、CPU/内存/时间限制；
8. 禁止把宿主机密钥、生产目录或任意终端暴露给模型。

**验收标准**：

- 模型不能读取授权仓库之外的文件；
- 未审批不能提交或修改受保护分支；
- 命令、网络和资源限制有效；
- 测试失败能明确区分代码失败和环境失败；
- 沙箱销毁后不残留凭据和临时文件。

### P6：Graph RAG、反馈和模型训练

**目标**：针对确有多跳关系问题或稳定数据规模后，再建设高级知识和模型能力。

**预计工作量**：3～6 个月以上，属于独立平台项目。

**实施内容**：

- 实体、关系、时间和来源抽取；
- 图数据库和 Graph RAG 查询；
- 多跳证据合并与冲突处理；
- 用户点赞、纠错、人工改写和质量回流；
- 企业数据集、脱敏、训练评测和模型发布；
- LoRA/微调只在 Prompt、RAG 和评测已经稳定后考虑。

**进入条件**：

- 固定评测集已经稳定；
- 真实问题确实存在跨文档关系推理需求；
- 企业数据具有合法、稳定、可脱敏的训练来源；
- 有独立模型评测、回滚和发布流程。

## 4. 依赖和发布顺序

```text
现有 Prompt / 审计
    ↓
P0 混合检索、Reranker、引用校验
    ↓
P1 Goal / Todo / Agent Loop
    ↓
P2 MCP 只读连接
    ↓
P3 多模态正式启用
    ↓
P4 Workflow / Workspace Agent
    ↓
P5 Vibe Coding / 沙箱
    ↓
P6 Graph RAG / 反馈 / 微调
```

P0 不依赖 P2～P5；P1 依赖现有执行事件和断点恢复；P4 依赖 P1 和 P2；P5 依赖 P1、审批和沙箱安全基线；P6 依赖稳定评测数据。

## 5. 统一开关、审计和回滚

每个阶段都必须具备：

- 配置开关，默认关闭新能力；
- `profile` 或版本字段；
- 运行事件和错误码；
- Prompt、工具集合、上下文和外部服务哈希；
- 灰度用户/Workspace 范围；
- 旧路径兼容；
- 一条配置回滚命令；
- 对应固定评测和失败样本。

推荐新增的审计字段：

```text
capability_profile
retrieval_mode
reranker_version
memory_hit
knowledge_hit
goal_id
todo_id
workflow_id
mcp_server
mcp_tool_version
source_type
stop_reason
verification_status
```

不记录完整 Prompt、知识正文、文件正文、原始 SQL、密钥或模型隐藏推理。

## 6. 资源和总体工作量

只做 P0～P2：

```text
单人约 8～14 周
新增运行内存约 1～2GB
```

做到 P3～P4：

```text
单人约 4～7 个月
新增运行内存约 2～4GB
多文件并发时另加 2～4GB
```

做到 P5：

```text
单人约 6～10 个月累计
每个代码沙箱约 500MB～2GB
```

做到 P6：

```text
单人约 8～15 个月累计
需要独立图数据库、数据集和模型评测流程
```

## 7. 近期执行建议

第一批只实施 P0：混合检索、Reranker、引用校验和长期记忆命中事件。完成固定评测后再实施 P1。P2 只选择一个企业只读系统作为样板，P3 只开放图片和扫描 PDF。P4～P6 以真实业务需求为准，不提前建设。

每一阶段通过代码测试、固定样本、权限测试和灰度指标后，才进入下一阶段。任何阶段出现来源错误、越权、审批绕过、无限循环或数据泄露，应立即关闭该阶段开关，保留已经验证的旧链路。
