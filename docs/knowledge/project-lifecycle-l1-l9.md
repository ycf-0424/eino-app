## 项目概况

本项目是一个可私有部署的中文企业智能助手。文档知识、项目长期记忆、会话数据和执行记录分开保存；问答链路优先使用项目文档，其次使用项目长期记忆，最后才使用通用模型兜底。

当前已实现的主要能力包括：

- Markdown、TXT、HTML、JSON、DOCX 和 PDF 文本的知识库索引与检索；
- Milvus 文档向量库，MySQL 会话、账号、记忆元数据和执行记录；
- 长期记忆的抽取、版本、来源和按用户隔离；
- 飞书登录和本地账号登录，多用户会话/记忆/执行记录隔离；
- HTTP、WebSocket、执行事件、审批、取消、限流、队列超时和健康检查；
- 备份、恢复演练、不可变镜像发布和镜像回滚；
- 固定评测集、路由评测、工具执行证据和拒答评测。

当前没有对外承诺完整的表格、演示文稿、音频、视频或内部业务系统操作能力。相关能力在后续阶段按需扩展。

## L2：设计架构与选定云服务

### 已记录架构

应用采用 Go 实现，Agent 编排和工具层基于 Eino。MySQL 保存会话、账号、长期记忆元数据和执行记录；Milvus 保存文档向量和独立的长期记忆向量；本地持久化目录保存 checkpoint、笔记和执行文件。生产聊天模型通过 OpenAI 兼容接口访问，Embedding 单独使用支持 BGE-M3 的远程服务。

部署采用 Docker Compose。生产环境使用独立 Compose 文件和固定镜像标签或 digest；应用只绑定服务器本机端口，由 OpenResty/1Panel 提供 HTTPS、域名、WebSocket 和反向代理。生产默认单副本运行。

### 选型理由和取舍

- MySQL 适合保存需要事务、归属和审计的结构化数据；
- Milvus 适合文档和长期记忆的向量检索，并与索引器、维度检查和增量清单配套；
- Docker Compose 让本地开发栈和单机生产栈的组件保持一致，降低部署复杂度；
- 模型和 Embedding 分开配置，避免把聊天接口误当作向量接口；
- 固定镜像版本便于发布追踪和无重建回滚。

### 已记录的后悔点或长期取舍

仓库没有一份正式的“选完之后后悔”访谈记录，但记录了几项明确取舍：单副本限流使用进程内令牌桶，多副本时需要改为 Redis；当前不做 token 预算；Milvus 和 Embedding 服务增加了运维依赖；Embedding 维度必须和向量集合保持一致，换模型时需要新集合或全量重建；本地小模型的技能自主路由能力不足，需要服务端确定性路由兜底。

## L3：准备并配置云环境

### 已记录流程

生产 bootstrap 的顺序是：准备生产环境变量和固定镜像，校验 Compose 配置，启动 MySQL/Milvus 等基础依赖，执行数据库迁移，创建管理员账号，启动应用，执行知识库和长期记忆索引，最后配置 HTTPS、域名、WebSocket 和登录回调。

配置通过部署机环境文件或 Secret 注入。生产需要数据库、聊天模型、独立 Embedding、飞书登录和指标访问配置。真实密钥不进入 Git，也不写入知识库。

飞书登录要求后台登记的回调地址与部署配置逐字符一致，并确认应用权限和可用范围。配置检查脚本会依次检查凭据有效性、健康接口、登录入口、授权地址一致性和伪造 state 的拒绝行为。

### 已记录的最费劲环节

运行复盘中最典型的配置问题有：

- 凭据非空不代表凭据有效，错误字符会一直到换 token 才暴露；
- 回调主机名、协议、端口或路径不一致会导致登录失败；
- Compose 没有透传新增环境变量时，宿主机配置正确但容器仍拿不到配置；
- 数据库备份需要额外权限，应用账号不能直接承担所有备份操作；
- 生产 Compose 与开发 Compose、开发数据卷必须严格分开。

### 待补充事实

仓库没有保存目标云服务器的真实账号权限清单、网络安全组、DNS 变更单、证书申请记录或最终域名。这些内容需要由部署方补充后再加入知识库。

## L4：开发环境构建与预览

### 已记录流程

本地开发使用 Go、Docker Compose、MySQL、Milvus、etcd、MinIO 和本地或远程模型服务。服务支持内置 Web 界面、HTTP、WebSocket、知识库索引和固定评测。生产环境切换为远程聊天模型和独立 Embedding，配置文件和数据卷与开发环境分开。

### 已记录的环境差异和问题

一次健康检查问题表现为容器中的 readiness 接口返回未授权。代码已经包含该路由，但镜像中的二进制仍是旧版本；仅看到“镜像构建成功”不足以证明产物已更新。通过检查容器内二进制、重新构建并强制重建容器后问题消失。

另一次机器重启后 Docker 引擎没有自动就绪，基础依赖容器退出。使用 Docker 官方启动方式恢复引擎，再补启动 Milvus、etcd 和 MinIO；应用在依赖恢复前出现的连接重试属于等待过程，依赖健康后 readiness 恢复。

## L5：发布上线、灰度与回滚

### 已记录发布方式

发布先构建固定版本镜像，再通过生产 Compose 以该版本启动，不使用会漂移的 `latest`。数据库迁移、管理员初始化、知识库索引和长期记忆索引使用同一镜像中的运维程序完成。发布和回滚都使用已有镜像，不在回滚时重新构建源码。

回滚方式是把生产配置切换到已验证的上一版本镜像，再由 Compose 重启应用。执行事件功能还提供运行时开关，出现问题时可关闭开关并重启，保留数据库表而不影响旧聊天路径。

### 已验证结果

本机独立生产测试栈已经完成两个固定版本之间的镜像切换；两个版本均达到 healthy，readiness 返回正常，回滚过程没有重新构建。优雅停机、限流、备份恢复和健康检查也完成过本机验证。

### 灰度状态

最新明确记录显示，目标环境的 3–7 天内部灰度尚未开始。灰度计划对象为少量内部用户，连续达到门槛后再决定扩大范围。仓库没有保存正式生产环境的发布失败记录或真实线上回滚记录，只有本机演练和测试环境问题。

## L7：发现异常与定位原因

### 已记录的代表性问题

1. **备份链问题**：真实演练发现备份账号权限不足、GTID 特权语句影响恢复、打包器镜像依赖网络、失败目录会被误选为最近备份。修复后增加最小权限备份账号、关闭不适合跨库恢复的 GTID 信息、固定本地打包器镜像并在失败时清理目录。
2. **旧镜像问题**：构建流程报告成功但容器内仍是旧二进制，导致 readiness 行为与源码不一致。通过验证产物本身和强制重建定位。
3. **模型路由问题**：模型把技能名当工具名调用，出现工具不存在的整轮失败；补充未知工具兜底和工具清单后硬失败消失，但小模型仍不主动加载技能，路由准确率长期偏低。
4. **登录配置问题**：凭据中的相似字符被误读，授权页能打开但换 token 失败。通过直接调用凭据校验接口和形近字符探测定位。
5. **多轮会话问题**：第一轮成功、第二轮快速返回归属不匹配错误。根因是事务钩子捕获了配置中的静态 owner，而请求使用的是登录态 owner；修复为按请求身份派生记忆作用域。
6. **失败会话问题**：一次失败回合留下空的助手占位消息，后续历史被模型拒绝，导致旧会话持续失败。修复为送模型前过滤无内容、无工具调用的失败占位消息，同时保留数据库记录用于审计。

### 如何发现

主要信号来自固定评测、HTTP 状态码、readiness 检查、数据库行数和会话分组、执行事件、容器退出码、恢复演练、日志中的错误原因，以及人工复现多轮对话。复盘中强调：不能只看“构建成功”或“有备份文件”，必须验证实际产物和可恢复内容。

### 长期未解决或待补充

- 单副本进程内限流尚未扩展为多副本共享限流；
- token 预算仍未实现；
- 小模型自主技能路由准确率偏低；
- 16 道执行类评测题缺少可判定的答案断言；
- 40 题回归缺少同题集、同模型、同配置和同知识库快照的严格前后基线；
- 目标服务器上的正式 HTTPS、域名、飞书回调和 3–7 天灰度记录仍待补充。

## L8：恢复服务与修复问题

### 止损原则

如果出现认证或跨用户数据泄露、备份/恢复失败、模型持续不可用、工具执行证据低于门槛或非超时 5xx 达到门槛，应停止扩大灰度范围，保留日志和当前版本，切回已经验证的固定镜像。

### 已采用的恢复方式

- 生产发布问题：切换到上一固定镜像并重启，不重新构建；
- 执行事件问题：关闭运行时开关，保留表结构，恢复旧聊天路径；
- 依赖不可用：通过 readiness 指出具体依赖，恢复 MySQL/Milvus/模型服务后自动恢复；
- 记忆后台任务失败：跳过当前任务，在后续周期重试，不把输入问题伪装成系统成功；
- 备份恢复：先校验清单和校验和，再导入临时库逐表比对，完成后删除临时库；
- 会话污染：保留失败记录和用户输入，过滤不能送给模型的空助手占位消息。

修复完成后，必须同时做单元测试、集成测试、端点回归和数据落库检查。仅仅看到服务重新启动不能算恢复完成。

- 将聊天模型与 Embedding 服务分离；更换 Embedding 时要求确认维度并重新索引；
- 修复记忆按请求 owner 归属、多轮会话和失败占位消息问题。

### 对照数据限制
