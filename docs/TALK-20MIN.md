### 一句话定位

> 这是一个基于字节 CloudWeGo Eino 框架构建的 Go AI Agent 应用，
> 约 9800 行业务代码 + 2650 行测试，具备工具调用、RAG 知识库、自动长期记忆、
> 人工审批中断、实时执行进度和内置 Web 界面，可用单机 Docker 完整拉起。

### 讲三件事

1. **不是套壳聊天框。** 一个真正能干活的 Agent 要解决的是：怎么让它调工具而不越权、
   怎么让它答不出来时承认不知道、怎么让用户看见它在干什么、怎么让它记住上次的结论。
   这四个问题就是本项目的主体。

2. **技术栈选择。** Eino v0.9.17（ADK Runner + Supervisor 多 Agent）、Go 1.26.3、
   MySQL + Milvus 双存储、Ollama 本地模型（qwen3.5:9b + bge-m3），
   通过改 config.yaml 三行即可切换火山方舟。模型可换是设计目标，不是巧合。

3. **演进方式。** 项目按 P0→P8 九个阶段递进，每阶段都有可独立验收的条目，
   路线图在 docs/ROADMAP.md。这个节奏本身是讲解的一条暗线：
   先工程基本盘，再 Agent 能力，最后生产化治理。

> 提示：开场别放代码。放一次真实对话截图或现场跑一句 `make run`，效果更好。

## 第 2 段 · 架构全景（4 分钟）

配合五层架构图讲。**自上而下走一遍，每层只说两句。**

### 接入层（cmd/server，1112 行）

- HTTP + WebSocket 双通道，另有 8 个 CLI 入口（console/indexer/eval/retrieve/
  sessions/session-migrate/memory-reindex/server）。
- 内置 Web UI 用原生 HTML/CSS/JS 写在 `internal/server/web/`，随 Go 二进制交付，
  **不需要 Node 构建链**。这是刻意的选择：一个 Go 项目不该为了聊天界面引入前端工程。

### 编排层（agent + chain + skill，789 行）

- `ChatAgent` 封装 Eino ADK Runner，对上暴露 `AskTo(ctx, query, writer)`，
  历史管理、持久化、审批中断全部收在里面，控制台和 HTTP 复用同一条路径。
- 多 Agent：Supervisor 调度 knowledge-agent 和 writer-agent。
  `knowledgeTools()` 显式裁剪知识 Agent 的工具集，让它拿不到文件写入能力。
- 两种执行模式并存：Agent 工具模式（模型自己决定调什么）和
  RAG Chain 固定模式（检索→格式化→生成，不给模型自由度）。要稳定就用后者。

### 能力层（rag + memory + tool + prompt，3457 行）

- 三大块：RAG 检索、自动长期记忆、受限工具。这是项目的重量所在，第 3 段深讲。
- 工具目前 4 个：时间、知识库检索、本地文件读取、笔记写入（需审批）。
- Prompt 全部模板化在 `internal/prompt/`，Skill 的业务规则用
  `wrapSkillInstruction()` 包一层隔离，防止拼接文本改写系统规则。

### 存储层

**职责边界要讲清楚，这是最容易被追问的点：**

```
MySQL   → 会话、消息、文档/分片元数据、长期记忆正文、执行记录
Milvus  → 只存向量：知识库分片 + 长期记忆，两个集合物理隔离
文件     → 降级方案，session.store 可切回 file 模式
```

关联方式：`knowledge_chunks.milvus_id` 和 `memories.milvus_id` 双向对应。
**向量库不存业务事实**，因为向量库不适合做事务、不适合做精确查询，
所以事实留在 MySQL，Milvus 只负责"找相似"这一件事。

### 横切治理

execution（执行事件）、observability（日志脱敏）、health（Ollama 健康检查）、
checkpoint（断点恢复）。这四个跨所有层，单独成包避免业务代码到处埋点。

## 第 3 段 · 技术纵深（8 分钟）

**只讲三个点，每个约 2 分半。统一用四步结构：现象 → 朴素做法为何不行 → 方案 → 代价。**

### 3.1 自动长期记忆：为什么不能把对话全塞进向量库

**现象**：希望 Agent 记住"这个项目用 Milvus 不用 Redis"这类结论，下次不用重说。

**朴素做法为何不行**：每轮对话都向量化写库。结果是向量库里 95% 是
"帮我看下这个报错""好的谢谢"这类噪声，真正有价值的结论被淹没，检索命中率反而下降。

**方案**：三级漏斗。

```
对话轮次 → extractor 抽候选（最多 5 条，取最近 8 条消息为上下文）
        → policy 规则判定
        → 只有 project_fact / decision / milestone / todo 四类进 Milvus
```

`internal/memory/policy.go` 的规则链：
- `Sensitive()` — 正则拦截密钥类内容，绝不入库
- `Suppressed()` — 拦截闲聊和无信息量表述
- `ExplicitCorrection()` — 识别"不对，应该是…"这类纠正，触发版本更新而非新增
- `ValidateCandidate()` — 长度与格式校验，超 500 字符丢弃

**关键点**：普通聊天只写 MySQL，不向量化。记忆有版本（保留 3 版），
可以被纠正、被删除，不是只增不减的垃圾堆。

**代价**：每轮多一次模型调用。用异步 worker + 租约机制（lease 180s、
最多重试 5 次、指数退避 2s→60s）消化延迟，不阻塞主对话。
这也是 memory 成为最大模块（1790 行）的原因——判定逻辑比抽取逻辑重得多。

### 3.2 执行事件流：并发写 WebSocket 是怎么踩坑的

**现象**：用户提交问题后，模型思考 30 秒界面一片空白，不知道是卡了还是在跑。
需要显示"正在检索知识库""已加载技能"这类真实进度。

**朴素做法为何不行**：让工具直接往 WebSocket 写事件。两个问题：
1. 工具层依赖了传输层，没法测试也没法复用到 HTTP 同步接口；
2. 多 Agent 场景下根 Agent 和子 Agent 并发 `WriteJSON`，gorilla/websocket 直接崩。

**方案**：
- 抽出 `internal/execution` 包和 Emitter 接口，工具只管发事件，不知道往哪发。
- WebSocket 端用**单一写循环**串行发送，正文 chunk 和执行事件
  **共用同一条单调递增 sequence**，保证同一 run 内事件与正文的相对顺序稳定。
- 背压策略：队列容量 256，满时允许丢中间事件并标记 `dropped=true`，
  前端凭 `after_sequence` 补取；但 `run_completed`/`run_failed`/`run_cancelled`
  三个终态**必须送达**，入队失败就主动断连并记日志，绝不静默丢弃。
- 协议版本化：`version` 整数，新增可选字段不升版本，改语义必须升。
  消费端遇到未知 type 或更高 version 就忽略该事件，不让整轮失败。

**一个容易忽略的细节**：审批中断时只发 `tool_started`，**不补 `tool_completed`**，
改由审批链路发 `approval_required`；恢复执行沿用原 run_id 继续递增 sequence，
不新建 run。否则界面上会出现一个永远"进行中"的幽灵调用。

**代价**：整套采集有 1556 行，且**默认关闭**（`execution_events.enabled: false`）。
这是灰度设计：关闭时完全不创建执行上下文，行为与上一版完全一致，出问题改配置即可回滚。

### 3.3 RAG 质量：证据优先，允许明确的通用兜底

**现象**：知识库问答最大的风险不是答不出来，是一本正经地胡说。

**朴素做法为何不行**：
1. 每次重建全量索引——文档一多就慢到不可用；
2. 检索有结果就交给模型——相似度 0.2 的无关片段也会被当依据。

**方案**：

索引侧（`internal/rag/documents.go` + `manifest.go`）：
- 稳定 ID + 内容哈希，重复 index 跳过未变化块，改一处只更一块
- 删除源文件会清理对应旧 ID，用跨进程锁防并发索引冲突
- 支持 Markdown/TXT/HTML/JSON/DOCX/PDF，标题感知切分（chunk 800、overlap 120），
  PDF 按页保留页码元数据

检索侧：
- `score_threshold: 0.50`，这个数字是拿本地 bge-m3 实测校准的
  （事实类问题实际最低约 0.54），不是拍脑袋
- 低于阈值先查项目长期记忆；仍无依据时允许通用模型回答，但必须标明不是项目内部资料结论
- 结果去重 + 引用标记，回答带 `sources` 可追溯到文档路径
- Prompt 注入防护：知识库文档里的恶意指令不能覆盖系统规则

输出侧（`internal/output/`）：统一 `answer` / `sources` / `confidence` / `error`
四字段结构化输出，业务方不用解析自然语言；非法 JSON 有纯文本降级。

**代价**：阈值校准需要真实评测。`cmd/eval` 跑固定问答集，
当前正确率 1.0、引用率 1.0、拒答率 1.0，平均耗时 4360ms。
拒答率 1.0 的含义是"该拒答的都拒答了"，这个指标比正确率更难做。

## 第 4 段 · 工程质量（4 分钟）

这段是把项目和"跑通了的 demo"区分开的地方。

### 测试分层

```
go test -p 1 ./...              → 2650 行单测，不连任何外部服务
-tags mysql_integration         → 真实 MySQL 集成测试
-tags integration               → 真实 Ollama + Milvus
go run ./cmd/eval               → 固定问答集端到端评测
```

**为什么分层**：默认测试不依赖外部服务，CI 才跑得动；
需要真实链路时用 build tag 显式开启。`-p 1` 是本机限制——并行编译会 OOM。

MySQL 集成测试覆盖的是真正难的部分：`StartRun` 幂等、`AppendEvents` 重复不入库、
`LinkRunMessage` 回填、`after_sequence` 补取、`RecoverStale` 修复超期 running 状态、
`DeleteBySession` 无孤儿数据。

### 灰度与回滚

`execution_events.enabled` 默认 false，关闭态和开启态都要通过全量测试。
回滚只需改配置重启，新表保留不删。**这是敢在生产上灰度的前提。**

### 安全边界

- 文件工具白名单：`local_files.roots` 显式列目录，越界直接拒绝，
  只读 UTF-8 文本和 DOCX 正文，不能写、不能执行，单文件上限 10MB
- 写操作（`write_note`）走 StatefulInterrupt 人工审批，
  审批后用同一 checkpoint Resume，跨进程可恢复
- 密钥从 .env / 环境变量注入，config.yaml 不存真实 Key；
  日志脱敏覆盖 JSON 字段、Bearer token、URL 内嵌密钥；
  Session 和 Checkpoint 不写入配置密钥
- 远程服务缺 Key 时启动即报错，不等到请求失败才暴露

### 资源治理

- 请求超时 180s、最大并发 2、同 Session 排队（`acquireSession`）
- 模型重试 3 次指数退避，区分可重试（网络/5xx/限流）与不可重试（参数错误）
- 会话历史治理：max 20 条 / 12000 字符，超出摘要压缩，30 天过期清理
- `/metrics` 暴露请求数、错误数、活动数、平均耗时
- Ollama 启动前健康检查，含 embedding 向量维度校验（1024），维度不匹配直接报错

### 可部署性

`make` 一条命令拉起：`infra-up` 起 MySQL/Milvus/etcd/MinIO，
`up` 构建并启动全套，`attu` 带 Milvus 管理界面。
Dockerfile 编译 Linux 静态二进制，容器内可访问宿主机 Ollama。

## 第 5 段 · 收尾（2 分钟）

### 诚实说边界

这一段千万别跳过，主动说边界比被问出来强：

- 身份体系目前只支持 `local_single_user`，**多人认证未做**
- 历史 JSON 会话到 MySQL 的迁移工具尚未完成验收（ROADMAP 中未勾选）
- 约 20 次工具调用的规模压测、浏览器人工验收未执行
- 本地 9B 模型复杂问题约 3 分钟，调试期建议切火山方舟

### 后续方向

1. 完成历史迁移与切换恢复演练，走完存储收口
2. 多人认证 + 权限，为多租户做准备
3. 执行事件采集的规模压测，确认首字延迟影响后逐步放量开关

### 收束一句

> 这个项目真正花时间的不是"接通模型"，而是三件事：
> 让 Agent 的每一步可观测、让它的权限边界明确、让它答不出来时承认不知道。
> 这些都不是框架送的，是要一行行写出来的。

## 讲解注意事项

**节奏**
- 第 3 段是拿分点，宁可少讲一个点也不要三个都讲浅
- 每段结束停 2 秒，给听众跟上的时间

**别做的事**
- 别逐个念包名和函数名，听众记不住
- 别念代码行，要念就投屏指着讲
- 别说"这个很简单"，也别说"这个很复杂"

**必答问题预演**
| 提问 | 回答要点 |
|------|---------|
| 为什么用 Eino 不用 LangChain？ | Go 原生、ADK 的 Runner/Checkpoint 抽象适合服务端、无 Python 运行时 |
| Milvus 是不是太重了？ | 是，所以 `rag.store` 可切 Redis Stack，学习期文档少用轻量方案 |
| 记忆会不会记错？ | 有版本（保留 3 版）、可纠正、可删除，敏感内容正则拦截不入库 |
| 并发只有 2 会不会太低？ | 本地 9B 模型的限制，配置项可调，瓶颈在模型不在服务 |
| 测试覆盖率多少？ | 2650/9810 约 27% 行数比，重点覆盖 execution、memory policy、config、agent 中间件 |

## 开场前 10 分钟准备

### 环境自检

```bash
# 1. 依赖起来（MySQL / Milvus / etcd / MinIO）
make infra-up

# 2. 静态检查 + 单测，确认现场代码是干净的
make check

# 3. 拉起点服务（本地模式，监听 18181）
make run
```

### 演示素材准备好

| 项目 | 命令 / 位置 | 现场是否演示 |
|------|------------|------------|
| 服务状态 | `curl localhost:18181/health` | 建议演示，1 秒出结果 |
| 指标 | `curl localhost:18181/metrics` | 建议演示，证明有可观测性 |
| RAG 原始检索分 | `make retrieve` | **强烈建议演示**，能直观看到 0.54 这类相似度分数，是第 3.3 段最有力的证据 |
| 评测 | `make eval` | 不现场跑（慢），用截图或提前跑好的结果 |
| Web 界面 | 浏览器打开 `localhost:18181` | 建议演示一次带执行进度的对话，但**模型慢，提前想好等多久** |

### 两个必须提前决定的事

1. **现场用哪个模型。** 本地 qwen3.5:9b 复杂问题约 3 分钟，现场演示会尴尬。
   建议把 `config.yaml` 的 openai 三行切到火山方舟，讲解时说明「为了演示切了云端」。
2. **要不要开执行面板。** `execution_events.enabled` 默认 false。
   如果要演示执行进度，提前改成 true 并重启，确认能正常出面板再上台；
   时间紧张就关着，讲解时口头说明即可。

### 顺手可讲的一句自我批评
