# 场景判断与技能暴露策略

## 技能选择

每轮请求使用现有模型调用，结合最近会话和技能摘要判断执行或澄清，不增加额外分类模型请求。技能目录（名称、描述、场景、不适用范围、能力状态）每轮进入系统提示词，正文只在模型调用 `load_skills` 时按需加载，且一次可以选择多个技能、一轮内可以多次调用。

技能 frontmatter 支持 `scenarios`、`not_for`、`required_tools` 字符串数组。工具依赖按服务实际注册名称精确匹配，缺失时在模型目录中明确标注；没有声明依赖不意味着可执行。接入新工具后应同步更新限制描述。

意图判断由提示词约束，不是强制的结构化路由协议，模型遵循效果需要真实模型验证。

## 暴露策略

技能名与技能目录属于内部实现，默认不向用户暴露，由 `Service.debugEnabled()`（即 config 的 `debug`）统一控制：

| 出口 | `debug: false`（默认） | `debug: true` |
| --- | --- | --- |
| `GET /skills` | 不注册路由，返回 404 | 返回技能名数组 |
| 前端技能选择器 | 隐藏 | 显示并加载技能列表 |
| 前端技能事件 | 不渲染（含 `load_skills` 工具调用本身） | 渲染 `skill_loaded` / `skill_preloaded` |
| 请求体 `skill` 字段 | 忽略 | 作为 `preferred` 预加载该技能正文 |
| 目录查询短路面 | 不生效，交给模型用能力语言回答 | 直接返回注册信息，无模型调用 |
| 提示词 | 禁止提及技能名，只能用能力语言回答 | 允许介绍与推荐技能名 |

设计取舍：

- 按名指定技能等价于把技能清单交给调用方，因此**传输层**（HTTP / WebSocket）在非调试模式下丢弃 `skill` 字段；**服务层 Go API 仍保留 `preferred` 能力**，供 CLI 与评测在进程内强制指定技能跑基线。
- 前端不自行判断。`GET /health` 与 WebSocket `ready` 帧回传 `debug` 状态，是否出现技能入口完全由后端决定。
- 非调试模式下模型仍会收到完整技能目录（否则无法选择技能），只是被约束不得把技能名复述给用户。这是提示词约束，属于软边界。

## 建议验证

调试模式（`debug: true`）：

- “目前都有什么技能”：直接列出目录，无模型调用。
- “我要总结 Word 工单，推荐什么技能”：推荐 documents，说明 DOCX 读取范围，不输出 HTML。
- “分析 Excel 并生成文件”：区分分析建议与未接入的文件生成能力。
- 上轮讨论 Word 工单后问“哪个技能适合”：利用上下文推荐。
- 无上下文问“哪个最适合我”：提供场景选项并追问用途。
- 即使选中 visualize，询问技能推荐仍不生成 HTML 示例。

非调试模式（默认）：

- `GET /skills` 返回 404，界面无任何技能入口。
- “你有哪些能力”：用能力语言回答，回答中不得出现任何技能名。
- 请求体带 `skill` 字段不改变路由结果。

元数据读取、目录不泄露正文、工具依赖匹配、目录查询分支及调试门禁由自动测试覆盖；这些测试不等于模型路由准确率评测。
